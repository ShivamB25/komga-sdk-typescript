SDK 2.0 is a breaking referential update from the historical SDK 1.x package. For users skipping versions, this guide also preserves the clean cutover from the historical 0.x service layer. The generated operations in this guide target the Komga 1.26.3 API schema: a client is created per integration, operation parameters are flat, and requests resolve to structured results unless you explicitly call `unwrap`.

## What changed

| Historical 0.x pattern | SDK 2.0 replacement |
| --- | --- |
| `createClient(...)` plus service instances | `createKomgaClient({ baseUrl, auth, headers, credentials, fetch })` |
| `new BookService(client).getById(id)` | `getBookById({ bookId: id }, { client })` |
| `new SeriesService(client).list(...)` | `getSeries({ seriesSearch, page, size, sort }, { client })` |
| Service-specific request/response classes | Generated operations and types from the API schema |
| `{ client, path, query, body }` grouped arguments | One flat operation parameter object, then `{ client }` |
| SDK-wide retry/cache/validation policy | Native Fetch plus policy code owned by the application |
| Legacy service/error/interceptor wrappers | `result.error`/`result.response` or explicit `unwrap` at the call site |

Do not carry over the removed service layer, Ky/Zod request wrappers, legacy error classes, or a global interceptor policy. If an integration needs retries, caching, timeout handling, or tracing, wrap `fetch` or the operation in that integration.

## Create a client

```typescript
import { createKomgaClient } from 'komga-sdk';

const client = createKomgaClient({
  baseUrl: process.env.KOMGA_URL!,
  auth: {
    type: 'apiKey',
    key: process.env.KOMGA_API_KEY!,
  },
});
```

The supported `auth` variants are API key and Basic Auth. `headers`, `credentials`, and a custom native `fetch` implementation are optional client settings. Do not copy a historical 0.x Bearer-auth configuration into `auth`: the current SDK 2.0 client does not expose a Bearer auth variant.

## Flatten every operation call

In the historical 0.x client, a call commonly looked like this:

```typescript
// Historical 0.x shape — do not copy this into an SDK 2.0 integration.
await bookService.list({
  query: { page: 0, size: 20 },
  body: { fullTextSearch: 'manga' },
});
```

In SDK 2.0, the generated names tell you where each value goes. `getBooks` has a required `bookSearch` body value; pagination and sorting remain flat:

```typescript
import { getBooks } from 'komga-sdk';

const result = await getBooks(
  {
    page: 0,
    size: 20,
    sort: ['metadata.title,asc'],
    bookSearch: { fullTextSearch: 'manga' },
  },
  { client },
);

if (result.error) {
  console.error(result.response?.status, result.error);
} else {
  for (const book of result.data?.content ?? []) {
    console.log(book.metadata.title);
  }
}
```

Path values use their generated names, such as `{ id: 'collection-123' }` for collection operations and `{ bookId: 'book-123' }` for book operations. Request bodies use generated DTO parameter names such as `collectionCreationDto`, `readProgressUpdateDto`, and `userUpdateDto`.

## Endpoint and operation mapping

Use the current generated operation rather than the old route directly:

| Historical 0.x endpoint or call | SDK 2.0 operation | SDK 2.0 parameter mapping |
| --- | --- | --- |
| `GET /api/v1/books` | `getBooks` | `bookSearch`, `page`, `size`, and `sort` are flat; the server endpoint is `POST /api/v1/books/list`. |
| `GET /api/v1/series` | `getSeries` | `seriesSearch`, `page`, `size`, and `sort` are flat; the server endpoint is `POST /api/v1/series/list`. |
| `GET /api/v1/series/alphabetical-groups` | `getSeriesAlphabeticalGroups` | Pass `{ seriesSearch }`; the generated endpoint is `POST /api/v1/series/list/alphabetical-groups`. |
| `GET /api/v1/series/{seriesId}/books` | `getBooks` | Use `bookSearch.condition.seriesId`, not a removed service method; paginate with flat `page`, `size`, and `sort`. |
| `GET /api/v1/age-ratings` | `getAgeRatings` | Use flat `library_id?: string[]`, `collection_id?: string[]`, `unpaged`, `page`, and `size`; the current endpoint is `GET /api/v2/age-ratings`. |
| `GET /api/v1/authors` | `getAuthors` | Use flat `search`, `role`, `library_id?: string[]`, `collection_id?: string[]`, `series_id?: string[]`, `readlist_id?: string[]`, and pagination; the current endpoint is `GET /api/v2/authors`. |
| `GET /api/v1/authors/names` | `getAuthorsNames` | Use the flat search, scope-array, and pagination keys; the current endpoint is `GET /api/v2/authors/names`. |
| `GET /api/v1/authors/roles` | `getAuthorsRoles` | Use flat scope-array and pagination keys; the current endpoint is `GET /api/v2/authors/roles`. |
| `GET /api/v1/genres` | `getGenres` | Use flat `search`, scope-array, and pagination keys; the current endpoint is `GET /api/v2/genres`. |
| `GET /api/v1/languages` | `getLanguages` | Use flat `search`, scope-array, and pagination keys; the current endpoint is `GET /api/v2/languages`. |
| `GET /api/v1/publishers` | `getPublishers` | Use flat `search`, scope-array, and pagination keys; the current endpoint is `GET /api/v2/publishers`. |
| `GET /api/v1/series/release-dates` | `getSeriesReleaseYears` | Replace release-date values with flat scope-array and pagination keys; the current endpoint is `GET /api/v2/series/release-years`. |
| `GET /api/v1/sharing-labels` | `getSharingLabels` | Use flat `search`, scope-array, and pagination keys; the current endpoint is `GET /api/v2/sharing-labels`. |
| `GET /api/v1/tags` | `getTags` | Use flat `search`, scope-array, `include?: 'SERIES' | 'BOOK' | 'BOTH'`, and pagination keys; the current endpoint is `GET /api/v2/tags`. |
| `GET /api/v1/tags/book` | `getTags` | Pass `include: 'BOOK'` with the flat scope-array and pagination keys; the current endpoint is `GET /api/v2/tags`. |
| `GET /api/v1/tags/series` | `getTags` | Pass `include: 'SERIES'` with the flat scope-array and pagination keys; the current endpoint is `GET /api/v2/tags`. |
| `PUT /api/v1/libraries/{libraryId}` | `updateLibraryById` | Pass `{ libraryId, libraryUpdateDto }`; the generated operation uses the current `PATCH` endpoint. |
| `GET /api/v1/collections/{id}` service call | `getCollectionById` | Pass `{ id }` and `{ client }`. |
| `GET /api/v1/readlists/{id}` service call | `getReadListById` | Pass `{ id }` and `{ client }`. |

All v2 referential list operations return a page. `getAuthors` returns `PageAuthorDto`, `getAgeRatings` returns `PageInteger`, and the other referential value operations return `PageString`; read values from `result.data?.content ?? []`. Scope identifiers use arrays wherever accepted (`library_id`, `collection_id`, `series_id`, and `readlist_id`). The `getTags` `include` value is `SERIES`, `BOOK`, or `BOTH`.

<Note>
Regeneration retains deprecated v1 exports for compatibility. When a v1 and v2 operation share a generated name, the legacy export receives a suffix such as `getAgeRatings1`, `getAuthorsNames1`, `getAuthorsRoles1`, `getGenres1`, `getLanguages1`, `getPublishers1`, `getSharingLabels1`, or `getTags1`. Other legacy exports retain names such as `getAuthorsDeprecated`, `getBookTags`, `getSeriesTags`, and `getSeriesReleaseDates`. These are not migration targets; do not import them in new code. Use the unsuffixed v2 operations in the table.
</Note>

`getBooksBySeriesId` remains generated only for compatibility with the schema and is marked deprecated. New SDK 2.0 code should use `getBooks` with a `seriesId` search condition so filtering and pagination use one current list operation.

## Handle results and errors

Generated operations resolve to `{ data, error, request, response }` and do not throw for an HTTP error by default. This makes it possible to inspect both the status and the server's error body:

```typescript
import { KomgaApiError, getCurrentUser, unwrap } from 'komga-sdk';

const result = await getCurrentUser(undefined, { client });
if (result.error) {
  console.error('Request failed', result.response?.status, result.error);
}

try {
  const user = unwrap(result);
  console.log(user.email);
} catch (error) {
  if (error instanceof KomgaApiError) {
    console.error(`Komga returned ${error.status}`, error.body);
  }
}
```

Use the structured result for expected failures (for example, an optional lookup). Use `unwrap` as the explicit throwing boundary for a request that must succeed. Successful no-content operations return `data: undefined`; that is not an error.

## Move request policies into application code

SDK 2.0 uses native Fetch and does not configure retries, caching, validation, or timeouts. Supply a custom Fetch implementation when policy belongs at the transport boundary:

```typescript
const client = createKomgaClient({
  baseUrl: process.env.KOMGA_URL!,
  fetch: async (input, init) => {
    for (let attempt = 0; attempt < 3; attempt += 1) {
      const response = await fetch(input, init);
      if (response.status < 500 || attempt === 2) return response;
    }
    throw new Error('unreachable');
  },
});
```

Keep policy-specific tests around this Fetch wrapper; the [Testing guide](/guides/testing) shows deterministic native `Response` fixtures.

## Migrate TypeScript imports

Generated request and response types are available from the package's `types` entry point:

```typescript
import type { BookSearch, ReadProgressUpdateDto } from 'komga-sdk/types';

const search: BookSearch = { fullTextSearch: 'manga' };
const progress: ReadProgressUpdateDto = { page: 12, completed: false };
```

Prefer inference from an operation call when a type is used only once. Do not maintain a parallel historical 0.x request schema: generated DTO fields and operation parameter names are the source of truth.

## Migration checklist

<Steps>
  <Step title="Create one client instance">
    Configure `createKomgaClient` with the server URL and the API key or Basic Auth credentials your application owns.
  </Step>
  <Step title="Replace service calls">
    Import generated operations directly and move path, query, and request values into their flat generated names. Pass `{ client }` as the second argument.
  </Step>
  <Step title="Update endpoint-specific searches">
    Replace legacy book/series list routes with `getBooks`/`getSeries`; use `bookSearch.condition.seriesId` for books in a series.
  </Step>
  <Step title="Choose result handling">
    Check `result.error` for non-throwing flows, or pass the result to `unwrap` when the call should raise `KomgaApiError`.
  </Step>
  <Step title="Move policies and tests">
    Put retries, caching, timeouts, and tracing in the custom Fetch or application layer. Inject native Fetch in unit tests and use a Komga instance for integration tests.
  </Step>
</Steps>
