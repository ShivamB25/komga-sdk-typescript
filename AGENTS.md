## OVERVIEW

`komga-sdk` is a zero-runtime-dependency TypeScript SDK generated from Komga's OpenAPI 3.1 contract. The public core is intentionally small:

- all API operations and wire types are generated by `@hey-api/openapi-ts`
- `src/client.ts` adds per-instance Komga authentication over native Fetch
- `src/result.ts` optionally unwraps generated result objects into typed exceptions
- generated code is isolated under `src/generated/`

The core does not contain domain service classes, handwritten DTO mirrors, Zod, Ky, retry policy, framework state, or query caching.

## NON-NEGOTIABLE INVARIANTS

1. **Never edit `src/generated/**` manually.** Change `scripts/generate.ts`, `openapi-ts.config.ts`, or the pinned OpenAPI version, then regenerate.
2. **Keep generated output isolated.** Generation may replace only `src/generated/`; it must never clean or overwrite handwritten `src` files.
3. **Keep the SDK flat.** Use tree-shakeable operation functions, not class-per-tag/domain wrappers.
4. **Keep the core Fetch-native.** Do not add Ky, Axios, retries, caching, or framework dependencies to the root package.
5. **Keep one canonical contract.** Do not handwrite DTO interfaces or Zod schemas that mirror generated OpenAPI types.
6. **Keep clients per-instance.** Do not root-export or configure the mutable generated singleton client.
7. **Keep HTTP errors non-throwing by default.** Generated calls return `{ data, error, request, response }`; `unwrap()` is the explicit throwing boundary.
8. **Keep runtime dependencies empty.** Optional validation/query/transport integrations belong in isolated subpath exports with optional peer dependencies, and only when demanded.
9. **Do not silently change retry semantics.** The raw SDK performs one request. Applications or optional TanStack Query adapters own retry policy.
10. **Emit Node-compatible ESM.** Generated and handwritten relative imports use `.js` specifiers; native Node 18 imports must keep working.

## UPDATING TO A NEW KOMGA RELEASE

Treat an API update as a compatibility review, not a blind regeneration.

### 1. Select an immutable release

Use a Komga release tag, never `master`:

```text
https://raw.githubusercontent.com/gotson/komga/<VERSION>/komga/docs/openapi.json
```

Update the URL in both:

- `openapi-ts.config.ts`
- `scripts/generate.ts` (`KOMGA_SPEC_URL`)

### 2. Review the OpenAPI delta

Before editing generated output, compare the old and new documents semantically:

- `info.version`
- path count and operation count
- added/removed/changed operations
- operation IDs and deprecated flags
- security schemes and per-operation security
- request/response content types
- added/removed/changed component schemas
- discriminator mappings, especially `SearchOperator*`
- binary, stream, text, and `204` responses

Do not preserve removed APIs with handwritten aliases. This package uses clean versioned cutovers.

### 3. Update and verify the checksum

Compute SHA-256 over the exact downloaded response bytes. Update `KOMGA_SPEC_SHA256` in `scripts/generate.ts` only after reviewing that the selected release document is authentic and expected.

Generation must fail on a checksum mismatch. Never weaken or bypass this check to make CI pass.

### 4. Review compatibility overlays

`scripts/generate.ts` contains targeted compatibility corrections for current upstream/generator behavior:

- repairs circular `SearchOperator*` aliases and discriminator literals
- treats Komga `font/*` responses as binary `Blob` data
- normalizes successful `204 No Content` data to `undefined`

For every Komga or Hey API upgrade:

1. Generate once in a disposable directory without assuming old patches still apply.
2. Check whether upstream now emits correct types/runtime behavior.
3. Remove a compatibility patch only when focused tests prove it is obsolete.
4. If output shape changed, update the structural normalization to fail loudly rather than silently matching the wrong code.

### 5. Regenerate

```bash
bun install
bun run generate
```

`bun run generate` must:

1. fetch the pinned OpenAPI document
2. verify SHA-256 before parsing
3. apply the structural schema overlay
4. generate into `.tmp/generated`
5. apply deterministic runtime/type corrections
6. replace only `src/generated`
7. restore the previous generated directory if the final rename fails
8. remove temporary generation artifacts

Expected current result: **130 paths and 165 flat operations**.

### 6. Review the generated API

Verify:

- every OpenAPI `operationId` has one exported flat function
- removed operations are actually removed
- new operations are root-exported through `src/index.ts`
- Basic and `X-API-Key` security metadata remains present where required
- public DTO/request/response names do not collide with handwritten exports
- generated imports contain Node-resolvable `.js` extensions
- no generated file appears outside `src/generated/`

### 7. Add behavior tests for contract changes

Tests must exercise real generated operations with an injected Fetch implementation. Do not mock generated functions or assert source text.

Cover every newly introduced behavior class:

- exact path and query serialization
- JSON request bodies
- Basic/API-key propagation
- binary/stream/text parsing
- successful void responses
- documented typed error bodies and original `Response`
- authentication-free endpoints where applicable

### 8. Run the release gate

```bash
bun run generate
bun run typecheck
bun run test
bun run build
npm pack --dry-run
```

Also run native Node ESM smoke imports for:

```text
komga-sdk
komga-sdk/client
komga-sdk/types
```

Smoke at least one built generated operation with API-key or Basic authentication. If response content behavior changed, smoke that built path too.

### 9. Update release metadata

After the generated contract and tests pass:

- update `package.json` version according to SemVer
- update the Komga/package versions at the top of this file
- update user-facing migration notes when public symbols or behavior changed
- regenerate the lockfile with Bun

Do not publish from a dirty tree or from mutable OpenAPI input.

## PUBLIC USAGE

```ts
import { createKomgaClient, getBookById, unwrap } from 'komga-sdk';

const client = createKomgaClient({
  baseUrl: 'https://komga.example.com',
  auth: { type: 'apiKey', key: process.env.KOMGA_API_KEY! },
});

const result = await getBookById({ bookId: 'book-123' }, { client });
const book = unwrap(result);
```

Supported authentication:

- HTTP Basic username/password
- `X-API-Key`
- unauthenticated requests
- cookie sessions through `credentials`
- custom session headers through `headers`

Komga does not use bearer/JWT authentication for its normal REST API. OAuth endpoints represent browser login/provider flows rather than a bearer-token SDK mode.

## OPTIONAL INTEGRATIONS

Do not add these to the core speculatively:

- generated Zod validation
- TanStack Query adapters
- React/Vue/Svelte hooks
- Ky/Axios transports

If demand exists, publish them through isolated subpaths such as `komga-sdk/react-query` with optional peer dependencies. The root entry point must remain framework-neutral and zero-runtime-dependency.

For TanStack Query integrations:

- generated query functions must reject API errors or use `throwOnError: true`
- the application owns `QueryClient`, retries, invalidation, SSR hydration, and cache lifetime
- do not combine transport retries with query retries

## MINTLIFY DOCUMENTATION

The maintained documentation site lives in `docs/mintlify/`. Its dependencies and lockfile are isolated from the SDK package. The local CLI is pinned in `docs/mintlify/package.json`; update it deliberately and run the full docs gate after every upgrade.

### Updating docs for an SDK or Komga release

1. Audit every live example against current generated symbols with CodeGraph. Never migrate calls by guessing parameter names.
2. Use the flat operation shape: `operation(parameters?, { client })`. Parameterless operations receive `{ client }` as their only argument.
3. Remove documentation for deleted services, grouped `{ path, query, body }` calls, Ky settings, handwritten SDK Zod schemas, legacy errors/interceptors, and Bearer auth.
4. Preserve substantive depth. Restore workflows, permissions, parameter semantics, state transitions, binary/void behavior, failure modes, and troubleshooting; remove only stale or repeated boilerplate.
5. Keep all maintained pages in `docs/mintlify/docs.json` navigation. Every MDX page needs `title` and `description` frontmatter.
6. Pin the API Reference OpenAPI URL to the same immutable Komga release as the SDK. Never use `master`.
7. Keep internal links root-relative without `.mdx` extensions and verify every code fence has a language tag.
8. Treat Mintlify accessibility warnings as release work: all media needs alt text and the primary color must meet WCAG AA.

### Docs dependency updates

From `docs/mintlify/`:

```bash
bun outdated
bun update --latest mint
bun install
```

Do not update the root SDK to an incompatible compiler merely because a prerelease is reported as latest. TypeScript remains pinned to 5.9.3 until the Hey API generation stack passes with TypeScript 7.

### Docs verification and preview

```bash
cd docs/mintlify
bun install
bun run --bun mint validate
bun run --bun mint broken-links
bun run --bun mint a11y
bun run --bun mint dev
```

The explicit `--bun` keeps the CLI usable on workstations whose globally selected Node version is newer than Mintlify supports. Prefer an active Node LTS release in CI.

`mint dev` is a local preview only; it does not publish. Before delivery, open the local site in Chromium and sample the introduction, quickstart, configuration, migration, a deep guide, and at least one generated API endpoint page.

Production docs deploy automatically after changes reach the connected repository branch only when the Mintlify GitHub App is configured. If no Mintlify check or preview appears on the PR, do not claim deployment succeeded; verify the integration or trigger deployment from the Mintlify dashboard after merge.

### Docs content boundaries

- The Mintlify site documents the published package, not generator internals unless the page is explicitly about maintenance.
- Optional TanStack Query, Zod, or custom transports may be shown as application-owned integrations, never as current root exports.
- `responseStyle` and `throwOnError` are per-operation options, not `createKomgaClient` defaults.
- Binary endpoints must document the generated runtime type actually returned (`Blob`, `string`, stream, or unknown), not assume every file-like response is a `Blob`.
- Successful `202` responses may carry unknown task data; successful `204` responses return `undefined`.
- A migration page may show old syntax in a clearly labeled “before” example. Live examples must use SDK 1.0.

OIDC trusted publishing requirements:

1. Use `npm publish`, not `bun publish`.
2. Use npm 11.5.1 or newer.
3. Clear placeholder `NODE_AUTH_TOKEN` values installed by setup-node.
4. Keep `id-token: write` permission in `.github/workflows/publish.yml`.

## ANTI-PATTERNS

- Editing generated files directly
- Generating from Komga `master`
- Updating the checksum without reviewing the spec bytes and semantic diff
- Adding class-based CRUD/domain wrappers over generated operations
- Reintroducing handwritten DTO or Zod mirrors
- Adding mandatory caching, retries, or UI frameworks to core
- Root-exporting the mutable generated singleton client
- Returning a different runtime shape than generated TypeScript declares
- Publishing extensionless ESM imports that fail in native Node
- Keeping deprecated aliases after a breaking API cutover
- Compressing docs by deleting unique workflows, permissions, edge cases, or troubleshooting
- Leaving maintained MDX pages hidden from `docs.json` navigation
- Treating `mint dev` as a production deployment
- Claiming Mintlify deployment without a GitHub App check or dashboard confirmation
- Updating Mintlify or root TypeScript without rerunning their separate validation gates
